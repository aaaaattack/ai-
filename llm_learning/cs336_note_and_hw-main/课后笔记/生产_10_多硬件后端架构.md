## 一、为什么需要多硬件后端抽象

现代 LLM 推理不仅要跑在 NVIDIA GPU 上，还需要支持：

| 硬件 | 厂商 | 编程模型 | vLLM 标识 |
|------|------|----------|-----------|
| NVIDIA GPU | NVIDIA | CUDA + Tensor Core | `CUDA` |
| AMD GPU | AMD | ROCm + HIP (CUDA-like) | `ROCM` |
| Intel GPU | Intel | XPU + oneAPI | `XPU` |
| Google TPU | Google | Pathways / libtpu | `TPU` |
| x86/ARM CPU | 各厂商 | PyTorch Native | `CPU` |
| Helion NPU | Houmo | TCIM Runtime | `OOT` / 仿冒 CUDA |
| 其他 NPU | 各厂商 | 自定义 | `OOT` |

**核心挑战**：

- Attention kernel 在不同硬件上完全不同（CUDA FlashAttention vs ROCm aiter vs 通用 Triton）
- 量化精度支持不同（H100 支持 FP8，A100 不支持）
- 通信后端不同（NCCL / XCCL / gloo / 自定义）
- 自定义算子不同（`torch.ops._C` vs `torch.ops._rocm_C` vs `torch.ops._xpu_C`）

**vLLM 的解法**：插件式平台发现 + 策略模式后端选择 + 模板方法算子分发。

### 3.3 `__getattr__` 魔法 — 隐式设备 API 代理

[`vllm/platforms/interface.py#L859-L878`](file:///e:/cs336_note_and_hw-main/cs336_note_and_hw-main/HLIEvLLM-1.4.0rc0/vllm/platforms/interface.py#L859-L878)

```python
def __getattr__(self, key: str):
    if key.startswith("__") and key.endswith("__"):
        raise AttributeError(key)

    device = getattr(torch, self.device_type, None)
    if device is not None and hasattr(device, key):
        attr = getattr(device, key)
        if attr is not None:
            return attr

    logger.warning(
        "Current platform %s does not have '%s' attribute.",
        self.device_type, key,
    )
    return None
```

**设计意图**：不用在每个用到 `current_platform.device_properties` 的地方加 `is_cuda()` 判断。如果 `self.device_type = "cuda"`，那么 `current_platform.synchronize()` 自动转发到 `torch.cuda.synchronize()`。

这让你可以用统一的方式写代码：
```python
current_platform.synchronize()    # CUDA → torch.cuda.synchronize()
current_platform.empty_cache()    # CUDA → torch.cuda.empty_cache()
current_platform.current_device() # CUDA → torch.cuda.current_device()
```

## 四、插件式平台发现系统

### 4.1 核心机制：`entry_points` + 插件函数

[`vllm/platforms/__init__.py#L204-L253`](file:///e:/cs336_note_and_hw-main/cs336_note_and_hw-main/HLIEvLLM-1.4.0rc0/vllm/platforms/__init__.py#L204-L253)

vLLM 使用 Python 的 `importlib.metadata.entry_points` 机制实现**无副作用插件发现**：

**内置平台插件**（硬编码映射）：

```python
builtin_platform_plugins = {
    "tpu":  tpu_platform_plugin,   # 检测 libtpu/Pathways
    "cuda": cuda_platform_plugin,  # 通过 NVML 检测 GPU
    "rocm": rocm_platform_plugin,  # 通过 AMDSMI 检测 GPU
    "xpu":  xpu_platform_plugin,   # 通过 torch.xpu.is_available()
    "cpu":  cpu_platform_plugin,   # 检测 vllm cpu build
}
```

**第三方（OOT）平台插件**通过 entry_points 注册：

[`vllm/plugins/__init__.py#L19-L66`](file:///e:/cs336_note_and_hw-main/cs336_note_and_hw-main/HLIEvLLM-1.4.0rc0/vllm/plugins/__init__.py#L19-L66)

```python
PLATFORM_PLUGINS_GROUP = "vllm.platform_plugins"

def load_plugins_by_group(group: str) -> dict[str, Callable]:
    from importlib.metadata import entry_points
    discovered_plugins = entry_points(group=group)
    plugins = {}
    for plugin in discovered_plugins:
        func = plugin.load()
        plugins[plugin.name] = func
    return plugins
```

**第三方硬件如何注册**：只需在其 `pyproject.toml` / `setup.cfg` 中声明：

```
[project.entry-points."vllm.platform_plugins"]
my_npu = "my_npu_package.platform:my_npu_plugin"
```

其中 `my_npu_plugin()` 是一个无副作用的检测函数，返回平台类的 qualified name（如 `"my_npu_package.platform.MyNpuPlatform"`）或 `None`。

### 4.2 解析流程：`resolve_current_platform_cls_qualname()`

```
1. 遍历内置插件 → 收集所有激活的平台名
2. 遍历 entry_points 发现的第三方插件 → 收集激活的 OOT 平台名
3. 优先级规则：
   - OOT 优先于内置
   - 多个 OOT 激活 → RuntimeError
   - 多个内置激活 → RuntimeError
   - 仅一个激活（内置或 OOT）→ 使用它
   - 零个激活 → 回退到 UnspecifiedPlatform
4. 返回平台类的 fully-qualified name
```

### 4.3 `current_platform` 全局单例

[`vllm/platforms/__init__.py#L283-L306`](file:///e:/cs336_note_and_hw-main/cs336_note_and_hw-main/HLIEvLLM-1.4.0rc0/vllm/platforms/__init__.py#L283-L306)

```python
_current_platform = None

def __getattr__(name: str):
    if name == "current_platform":
        global _current_platform
        if _current_platform is None:
            platform_cls_qualname = resolve_current_platform_cls_qualname()
            _current_platform = resolve_obj_by_qualname(platform_cls_qualname)()
        return _current_platform
```

通过模块级 `__getattr__` 实现**惰性初始化**：
- 首次 `import vllm.platforms.current_platform` 时才触发检测
- 之后直接返回缓存的实例
- 这样 OOT 插件可以在 `import vllm` 之后再注册，不影响检测

### 4.4 以 CUDA 插件为例 — 无副作用检测

[`vllm/platforms/__init__.py#L60-L108`](file:///e:/cs336_note_and_hw-main/cs336_note_and_hw-main/HLIEvLLM-1.4.0rc0/vllm/platforms/__init__.py#L60-L108)

```python
def cuda_platform_plugin() -> str | None:
    try:
        from vllm.utils.import_utils import import_pynvml
        pynvml = import_pynvml()
        pynvml.nvmlInit()
        try:
            is_cuda = (
                pynvml.nvmlDeviceGetCount() > 0
                and not vllm_version_matches_substr("cpu")
            )
        finally:
            pynvml.nvmlShutdown()   # 关键：检测完立即释放 NVML
    except Exception as e:
        ...
    return "vllm.platforms.cuda.CudaPlatform" if is_cuda else None
```

**设计要点**：
- 使用 NVML 而非 `torch.cuda.is_available()`，因为 `torch.cuda` 会初始化 CUDA 上下文（副作用）
- `nvmlInit()` / `nvmlShutdown()` 确保无资源泄漏
- 返回 `str`（类路径）而非实例，避免过早导入

这是平台抽象中最关键的一层 —— 同一模型、不同硬件上，attention 内核完全不同。

### 5.2 选择器：优先级 + 配置验证

[`vllm/v1/attention/selector.py#L52-L102`](file:///e:/cs336_note_and_hw-main/cs336_note_and_hw-main/HLIEvLLM-1.4.0rc0/vllm/v1/attention/selector.py#L52-L102)

```python
def get_attn_backend(head_size, dtype, kv_cache_dtype, use_mla, ...):
    """统一入口，根据配置选择最优 attention 后端"""
    # 1. 构建 AttentionSelectorConfig
    attn_selector_config = AttentionSelectorConfig(
        head_size=head_size, dtype=dtype,
        kv_cache_dtype=kv_cache_dtype, block_size=block_size,
        use_mla=use_mla, ...
    )
    # 2. 委托给 current_platform → 调用优先级排序 + validate
    attention_cls = current_platform.get_attn_backend_cls(
        backend, attn_selector_config=attn_selector_config, num_heads=num_heads
    )
    # 3. 动态导入类 + 设置 KV cache layout
    backend = resolve_obj_by_qualname(attention_cls)
    return backend
```

**AttentionSelectorConfig** 包含了影响 attention 选择的所有配置：
- 模型级：`head_size`, `use_mla`, `use_sparse`, `attn_type`
- dtype 级：`dtype`, `kv_cache_dtype`
- 内存级：`block_size`

### 5.3 CUDA 平台的优先级排序

[`vllm/platforms/cuda.py#L282-L374`](file:///e:/cs336_note_and_hw-main/cs336_note_and_hw-main/HLIEvLLM-1.4.0rc0/vllm/platforms/cuda.py#L282-L374)

流程：

```
1. 如果用户指定了 --attention-backend → 直接验证该后端
2. 否则 → get_valid_backends() 对所有后端按优先级排序
3. 逐个调用 backend.validate_configuration(device_capability, head_size, ...)
```

## 六、CustomOp 跨后端算子分发

这是 vLLM 中**最核心的"一个接口、多硬件实现"机制**。

### 6.1 CustomOp 基类

[`vllm/model_executor/custom_op.py#L103-L207`](file:///e:/cs336_note_and_hw-main/cs336_note_and_hw-main/HLIEvLLM-1.4.0rc0/vllm/model_executor/custom_op.py#L103-L207)

```python
class CustomOp(nn.Module):
    """算子基类。dispatch_forward() 按平台选择具体实现。"""

    def __init__(self, *, enforce_enable=False, compile_native=False):
        self._forward_method = self.dispatch_forward(compile_native)

    def forward(self, *args, **kwargs):
        return self._forward_method(*args, **kwargs)

    # ---- 各平台实现（子类覆盖）----
    def forward_native(self, *args, **kwargs):
        """纯 PyTorch 实现，可 compile"""
        raise NotImplementedError

    def forward_cuda(self, *args, **kwargs):
        raise NotImplementedError

    def forward_hip(self, *args, **kwargs):
        return self.forward_cuda(*args, **kwargs)  # HIP 默认兼容 CUDA

    def forward_xpu(self, *args, **kwargs):
        return self.forward_native(*args, **kwargs)  # XPU 默认 fallback

    def forward_cpu(self, *args, **kwargs):
        return self.forward_native(*args, **kwargs)

    def forward_tpu(self, *args, **kwargs):
        return self.forward_native(*args, **kwargs)

    def forward_oot(self, *args, **kwargs):
        return self.forward_native(*args, **kwargs)  # OOT 默认 fallback

    def dispatch_forward(self, compile_native: bool):
        """根据 current_platform 选择 forward 方法"""
        if not self.enabled():
            return self.maybe_compile(self.forward_native, enable=compile_native)

        if current_platform.is_rocm():
            return self.forward_hip
        elif current_platform.is_cpu():
            return self.forward_cpu
        elif current_platform.is_tpu():
            return self.forward_tpu
        elif current_platform.is_xpu():
            return self.forward_xpu
        elif current_platform.is_out_of_tree():
            return self.forward_oot
        else:
            return self.forward_cuda   # 默认 CUDA
```

### 6.2 设计模式分析

**模板方法模式**：
- `dispatch_forward()` 定义了调度骨架（算法步骤固定）
- 每个 `forward_*` 方法是钩子（子类可覆盖具体实现）

**默认兼容策略**：
- `forward_hip` → fallback 到 `forward_cuda`（ROCm 兼容 CUDA 算子）
- `forward_xpu/cpu/tpu/oot` → fallback 到 `forward_native`（纯 PyTorch）
- 这意味着一个 CustomOp 子类只需实现 `forward_cuda()` + `forward_native()`，其他平台自动 fallback

**启用/禁用控制**：
```python
# 编译配置中通过 custom_ops 控制：
# "all" → 所有平台原生 kernel 启用
# "none" → 全部回退 forward_native（用于 torch.compile）
# "+fused_moe" → 启用特定算子
```

### 6.3 实际例子：cutlass_scaled_mm

[`vllm/_custom_ops.py#L913-L924`](file:///e:/cs336_note_and_hw-main/cs336_note_and_hw-main/HLIEvLLM-1.4.0rc0/vllm/_custom_ops.py#L913-L924)

```python
def cutlass_scaled_mm(a, b, scale_a, scale_b, out_dtype, bias):
    if current_platform.is_rocm() or not cutlass_compatible_b:
```

## 七、OOT (Out-of-Tree) 平台机制

### 7.1 OOT 是什么

OOT = **完全不在 vLLM 主仓库中**的第三方硬件平台。vLLM 通过三层机制支持 OOT：

| 层级 | 机制 | 作用 |
|------|------|------|
| **平台发现** | `entry_points("vllm.platform_plugins")` | 注册自定义检测函数 |
| **算子替换** | `CustomOp.register_oot()` / `PluggableLayer.register_oot()` | 用自定义类替换内置算子 |
| **kernel 注入** | `Platform.import_kernels()` / `import_ir_kernels()` | 加载自定义 C++/CUDA 扩展 |

### 7.2 OOT 平台开发的最小步骤

假设你要接入一个名为 "MyNPU" 的硬件：

**步骤 1**：定义平台类：
```python
# my_npu/platfrom.py
from vllm.platforms import Platform, PlatformEnum

class MyNPUPlatform(Platform):
    _enum = PlatformEnum.OOT
    device_name = "mynpu"
    device_type = "mynpu"
    dispatch_key = "CPU"          # 或注册到 PyTorch 的新 backend
    dist_backend = "mynpu_nccl"  # 或 gloo

    @classmethod
    def get_attn_backend_cls(cls, ...):
        return AttentionBackendEnum.CUSTOM.get_path()

    def forward_oot(self, *args, **kwargs):
        """自定义算子 forward"""
        return self.mynpu_kernel(*args, **kwargs)
```

**步骤 2**：注册插件函数：
```python
# my_npu/__init__.py
def my_npu_plugin() -> str | None:
    try:
        import my_npu_hal
        if my_npu_hal.device_count() > 0:
            return "my_npu.platform.MyNPUPlatform"
    except:
        pass
    return None
```

**步骤 3**：声明 entry_point：
```toml
# pyproject.toml
[project.entry-points."vllm.platform_plugins"]
my_npu = "my_npu:my_npu_plugin"
```

**步骤 4**：安装后就生效了——不需要修改 vLLM 源码。

### 7.3 OOT vs 内置平台的关键区别

| 维度 | 内置平台 | OOT 平台 |
|------|----------|----------|
| 代码位置 | vLLM 主仓库内 | 第三方包 |
| 发现方式 | 硬编码 in `builtin_platform_plugins` | entry_points 动态发现 |
| 优先级 | 低于 OOT | 高于内置 |
| 算子分发 | `forward_cuda/hip/xpu` | `forward_oot` |
| 典型场景 | CUDA/ROCm/XPU/TPU/CPU | Houmo NPU、寒武纪、昇腾 |

## 八、Houmo / HLIEvLLM 的接入方式

### 8.1 当前方式：混合 CUDA 平台

HLIEvLLM 1.4.0 中，**Houmo 并没有注册为独立的 OOT 平台**，而是：

1. **复用 CUDA 平台**：在 `platforms/__init__.py` 中直接修改了 `current_platform` 的初始化逻辑

[`vllm/platforms/__init__.py#L262-L281`](file:///e:/cs336_note_and_hw-main/cs336_note_and_hw-main/HLIEvLLM-1.4.0rc0/vllm/platforms/__init__.py#L262-L281)

```python
# 原版 vLLM 的惰性初始化被注释掉
# current_platform: Platform = None

# Houmo 改成了注释 + 环境变量预设：
ENV_DEFAULTS = {
    "HDPL_PLATFORM": "ASIC",
    "TCIM_BACKEND": "Xh2HalBackend",
    "HM_PLATFORM": "2",
}
for env_name, default_value in ENV_DEFAULTS.items():
    os.environ[env_name] = os.getenv(env_name, default_value)

# 然后 current_platform 仍然走惰性初始化，但实际检测的还是 CUDA 平台
# 因为 Houmo Helion NPU 需要 CUDA 兼容路径
```

2. **NPU kernel 通过插件 whl 注入**：之前笔记提到的 `vllm-houmo-plugin` 通过 `entry_points("vllm.general_plugins")` 注册，在 `load_general_plugins()` 时注入自定义 kernel

### 8.2 为什么不用独立 OOT 平台

从 Houmo 的技术架构来看：
- Helion NPU 的 TCIM Runtime 在 HAL 层做了 CUDA API 的 forwarding
- NPU 代码编译为 CUDA GPU 代码（`.hmm`）
- 推理时 `cudaMemcpy` / `cuLaunchKernel` 被 HAL 拦截转发到 NPU
- 因此对 vLLM 来说，当前仍然是"看起来像 CUDA GPU 的设备"

### 8.3 未来的可能性

如果 Houmo 未来要把 Helion 注册为真正的独立 OOT 平台：

```
优势：
  - 不再需要修改 vLLM 源码（仅靠 entry_points 注册）
  - 可以自定义 attention 后端（AttentionBackendEnum.CUSTOM）
  - 可以自定义量化配置
  - 升级 vLLM 版本更平滑

挑战：
  - 需要实现完整的 Platform 子类
  - 需要自定义 attention backend
  - 需要处理 CUDA-like 代码的兼容性
```

## 十、总结

### 核心设计模式

| 模式 | 在哪里 | 解决什么问题 |
|------|--------|------------|
| **插件式发现** | `platforms/__init__.py` + `plugins/__init__.py` | 不修改 vLLM 源码就能接入新硬件 |
| **策略模式** | `AttentionBackendEnum` + `get_attn_backend()` | 同一模型自动选择最优 attention kernel |
| **模板方法** | `CustomOp.dispatch_forward()` + `forward_*` | 同一算子在不同硬件上使用不同实现 |
| **单例** | `current_platform` 全局惰性初始化 | 全代码库统一硬件判断入口 |
| **钩子** | `pre_register_and_update / apply_config_platform_defaults / check_and_update_config` | OOT 平台在配置生命周期的三个阶段介入 |

### 和你工作的关联

1. **理解 HLIEvLLM 为什么这样改**：Helion NPU 目前走 CUDA 平台路径，通过 HAL 层做 API forwarding 和 `.hmm` 编译产物
2. **与编译器团队讨论**：如果未来需要把 Houmo 注册为独立 OOT 平台，需要实现哪些接口
3. **与量化团队讨论**：`supported_quantization` 和 `verify_quantization()` 如何影响量化方案的平台兼容性
4. **客户方案**：当客户问"支持什么硬件"时，知道 vLLM 的底层设计和 Houmo 在其中的位置
