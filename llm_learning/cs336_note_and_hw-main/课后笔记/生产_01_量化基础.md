## 一、为什么需要量化？

### 1.1 显存与带宽压力

```
Qwen3-8B (FP16):
  权重: 8B × 2 bytes = 16GB
  + KV Cache + 激活值 → 轻松超过 24GB

Qwen3-8B (W4A16, GPTQ):
  权重: 8B × 4 bits / 8 = 4GB
  激活: 仍是 FP16（不下线，不省）
  省 75% 权重大小 = 能在更小显存的卡上跑

Qwen3-8B (W8A8, SmoothQuant):
  权重: 8GB, 激活: 8GB
  矩阵乘用 INT8 → 吞吐 ×2
```

### 1.2 Roofline 视角

```
Decode 阶段的算术强度 ≈ 3 FLOPs/Byte（访存瓶颈）
  → 减少权重访存: Weight INT4 可以把部分 bottleneck 从访存移向计算
  → 减少 KV Cache 访存: KV INT8 直接减少 decode 阶段的主流访存量
```

## 二、量化数学基础

### 2.1 基本公式

```python
# 浮点 → 定点（量化）
x_quantized = round((x_fp - zero_point) / scale)
# 限制范围
x_quantized = clamp(x_quantized, q_min, q_max)

# 定点 → 浮点（反量化）
x_fp = x_quantized × scale + zero_point
```

### 2.2 参数计算

```python
# 对称量化 (zero_point = 0)
max_abs = max(|x_fp|)
scale = max_abs / (2^(bits-1) - 1)       # INT8: max_abs / 127

# 非对称量化
x_min, x_max = x_fp.min(), x_fp.max()
scale = (x_max - x_min) / (2^bits - 1)   # INT8: range / 255
zero_point = round(-x_min / scale)
zero_point = clamp(zero_point, 0, 2^bits-1)
```

### 2.3 对称 vs 非对称

```python
# 对称量化示例 (适合权重，通常对称分布在 0 附近)
x = [0.5, -0.3, 0.0, 0.8, -0.1]
max_abs = 0.8
scale = 0.8 / 127 = 0.0063
INT8 = [79, -48, 0, 127, -16]
# 缺点: [-127, +127] 不对称，-128 没用上（但实际影响很小）

# 非对称量化示例 (适合激活值，ReLU 后 >=0)
x = [0.1, 0.5, 0.8]
scale = (0.8 - 0.1) / 255 = 0.00275
zero_point = round(-0.1 / 0.00275) = -36
INT8 = [0, 146, 255]
# 优点: 充分利用 [0, 255] 全范围
# 缺点: zero_point 非零 → 矩阵乘多一次减法
```

## 三、量化粒度

| 粒度 | Scale 个数 (W: 4096×4096) | 精度 | 计算复杂度 |
|---|---|---|---|
| per-tensor | 1 | 低 | 最简单 |
| per-channel (沿输出维) | 4096 | 中 | 标准方案 |
| per-token (沿输入维) | 4096 (每行) | 中 | 激活值常用 |
| per-group | 128×32=4096 个 | 高 | **GPTQ/AWQ 核心** |

### 3.1 Per-channel 量化

```python
# 权重矩阵 W: (out_features, in_features) = (4096, 4096)
# per-channel (沿 out_features 维 = 每行一个 scale)

scales = torch.zeros(4096)          # 每行一个 scale
for i in range(4096):
    scales[i] = W[i, :].abs().max() / 127
    W_int8[i, :] = round(W[i, :] / scales[i])

# 反量化: W_fp = W_int8 * scales.unsqueeze(-1)
```

**为什么比 per-tensor 好？**

```
per-tensor: 整矩阵 1 个 scale → W[0,:] 的 outlier 会拉低整个矩阵的 scale
per-channel: 每行独立 scale → 每行用自己最合适的范围 → 量化误差小得多
```

### 3.2 Per-token 量化（激活值）

```python
# 激活值 X: (seq_len, in_features)
# per-token (沿 seq_len 维 = 每行一个 scale)

# 每个 token 的激活值分布不同 → 每行自己的 scale
scales = X.abs().max(dim=-1) / 127         # (seq_len,)
X_int8 = round(X / scales.unsqueeze(-1))
```

### 3.3 Per-group 量化（GPTQ/AWQ）

```python
# 权重 W: (4096, 4096)
# 分成 group_size=128 的组 → 每组一个 scale

groups = W.reshape(-1, 128)               # (4096×4096/128 = 131072, 128)
scales = groups.abs().max(dim=-1) / 127   # (131072,)
# 粒度介于 per-channel 和 per-element 之间 → 精度接近 per-element
```

## 四、推理中的三类量化目标

### 4.1 Weight-only (W4A16)

```
权重: INT4 → 4 bits
激活: FP16 → 16 bits

前向计算:
  读 INT4 权重 → 解压为 FP16 → FP16 matmul

省什么:
  - 模型文件: 16GB → 4GB
  - 权重显存带宽 (decode 阶段读每层权重)
  - 不省激活和中间结果
```

### 4.2 Weight + Activation (W8A8)

```
权重: INT8, 激活: INT8
矩阵乘: INT8 @ INT8 → INT32 → 反量化 → FP16

省什么:
  - 矩阵乘算力: INT8 吞吐是 FP16 的 2 倍 (A100 Tensor Core)
  - 权重和激活的显存带宽
```

### 4.3 KV Cache 量化 (KV INT8)

```
KV Cache: K, V 从 FP16 → INT8
省什么:
  - decode 阶段的 KV Cache 显存带宽（decode 是访存瓶颈！）
  - KV Cache 显存占用（省 50%: 16GB→8GB per 层组）
  
不对模型本身做量化 → 和 W4/W8 方案叠加使用
```

## 五、量化对已学算子的影响

### 5.1 RMSNorm — "不要量化 Norm 的计算"

```python
# RMSNorm.forward (第1课)
variance = x.pow(2).mean(-1, keepdim=True)
x = x * torch.rsqrt(variance + eps)
x = x * weight

# 量化策略:
# weight 可以 W8（per-channel scale） ← 精度损失小
# variance 计算用 FP32（第1课已解释：需要高精度防止溢出）
# rsqrt 结果用 FP16（精度够）
```

**Houmo 对应**：Helion 有 `rms_norm_fp8` kernel（见 `autotune_helion_kernels.py:15`），但 norm 本身的计算大概率仍用高精度，只是 weight 是 FP8。

### 5.2 Linear (矩阵乘) — "量化的主战场"

```python
# FP16 矩阵乘
Y = X @ W.T          # X: FP16, W: FP16 → Y: FP16

# W8A8 矩阵乘
X_int8 = round(X / scale_x)
W_int8 = round(W / scale_w.unsqueeze(-1))
Y_int32 = X_int8 @ W_int8.T           # INT8@INT8 → INT32 累加
Y_fp16 = Y_int32.float() * scale_x * scale_w  # 反量化

# 关键: INT32 累加器避免溢出
# scale_x × scale_w 可能非常小 → 需要仔细处理
```

### 5.3 SwiGLU — "gate和up合并后的量化挑战"

```python
# nano-vllm 的 Qwen3MLP (第3课)
gate_up = self.gate_up_proj(x)        # MergedColumnParallelLinear
x, y = gate_up.chunk(2, -1)           # gate 和 up 对半切
out = silu(x) * y

# 量化问题:
# gate_up_proj 是合并权重 → gate部分和up部分共享 scale?
#   共享: 简单但可能精度差 (gate和up的分布可能不同)
#   分开: 精度好但需要改 weight_loader 和量化逻辑
```

### 5.4 RoPE — "不需要量化"

```python
# RoPE.forward (第2课)
q = apply_rotary_emb(q, cos, sin)     # 在 FP16 下做

# 为什么不量化?
# cos/sin 是三角函数 → 值域 [-1, 1]
# FP16 的 10 位有效数字 → 精度完全足够
# 量化为 INT8 反而增加误差
```

### 5.5 Softmax — "精度最敏感的算子"

```python
# Softmax.forward (第4课)
x = x - x.max()
x_exp = exp(x)           # ← exp 对输入极其敏感
return x_exp / x_exp.sum()

# 量化策略:
# 至少 FP16 (10 位有效数字比 bf16 的 7 位好)
# 通常 FP32（logits 范围大时）
# 这就是为什么 nano-vllm Sampler 写: logits.float()
```

### 5.6 Attention — "scale 因子需要重新 calibration"

```python
# Attention (第5课)
scores = Q @ K.T / sqrt(d_k)          # QK 都是 INT8?
# sqrt(d_k) 在 FP16 下是固定常数, 没问题
# 但 Q@K.T 如果是 INT8@INT8 → INT32, scale 因子变复杂

attn_weights = softmax(scores)
attn_weights @ V
# softmax 本身精度敏感 → 至少 FP16
# V 可以是 INT8 → 乘完反量化
```

## 七、思考题

1. **为什么 Weight 可以用 per-channel 量化，但 Activation 通常要用 per-token？**
   - 提示：Weight 是静态的（训练完就固定）→ per-channel scale 编译时确定。Activation 每次不同 → per-token 在运行时计算

2. **RMSNorm 的 `weight` 参数应该量化吗？**
   - 提示：weight 是 (d_model,) 的向量，FP16 → INT8 误差极小。但 norm 的输入已经归一化过，weight 的极值也很稳定 → 量化安全

3. **KV Cache 量化为什么对 decode 特别有效？**
   - 提示：decode 算术强度 ≈ 3 FLOPs/Byte，访存瓶颈。KV Cache 是 decode 的主要访存来源 → 减半 KV Cache 大小 = 近似减半访存量

4. **对称量化中，INT8 范围 [-127, +127] 不对称（-128 没用上），为什么几乎不影响精度？**
   - 提示：权重大致 N(0, σ²) → 对称分布 → -128 和 +127 都不常用到 → 丢失 -128 影响极小
