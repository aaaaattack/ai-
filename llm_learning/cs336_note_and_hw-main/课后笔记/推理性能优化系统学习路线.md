## 一、推理优化的核心心智模型

### 1.1 Prefill vs Decode 的根本区别

```
Prefill (首次推理):
  输入: [t1, t2, ..., t512]  一次性处理所有 prompt token
  特点: 计算密集 (Compute-Bound)，大量矩阵乘
  瓶颈: GPU 算力 (Tensor Core 利用率)
  优化方向: Kernel 融合、Tensor Core 调优、大 batch

Decode (自回归生成):
  输入: [t513]               每次只处理 1 个新 token
  特点: 访存密集 (Memory-Bound)，大量 KV Cache 读取
  瓶颈: 显存带宽 (HBM bandwidth)
  优化方向: KV Cache 量化、减少访存、CUDA Graph
```

### 1.2 Roofline 模型与算术强度

```
算术强度 = 计算量 (FLOPs) / 访存量 (Bytes)
```

Roofline 图：X 轴是算术强度，Y 轴是可达算力。转折点 = 峰值算力 / 峰值带宽。

| 阶段 | 算术强度 (FLOPs/Byte) | GPU 转折点 (A100: 156) | 结论 |
|---|---|---|---|
| Prefill (batch=1) | ~50-200 | ~156 | 偏计算瓶颈，大 batch 时更明显 |
| Decode (batch=1) | ~2-5 | ~156 | **严重访存瓶颈** |
| Decode (batch=32) | ~8-15 | ~156 | 仍访存瓶颈，但有所缓解 |

**核心结论**：Decode 阶段优化的本质是**减少从 HBM 读取的数据量**。这是量化（特别是 KV Cache 量化）和算子融合的核心价值。

## 三、第0步：Profiling 方法论（先学这个）

### 原则：不 profile 不优化

```
1. 测量基线 → 2. 找到瓶颈 → 3. 形成假设 → 4. 优化 → 5. 验证 → 回到 1
```

### 3.1 从粗到细的 profiling 层级

```
层级1: 端到端指标
  吞吐 (tokens/s)、TTFT (首 token 延迟)、TPOT (每 token 延迟)
  → vLLM 内置统计 / 业务打点

层级2: 阶段分解
  Tokenize → Prefill → Decode → Sample → Detokenize
  → nano-vllm LLMEngine.generate 的 prefill/decode 吞吐统计

层级3: 模块/函数耗时
  每个 Transformer Block 的 Attn vs FFN 占比
  → Python timeit / NVTX 手动打标

层级4: 算子级耗时
  QKV Proj vs Attention vs Norm vs SwiGLU 各占多少
  → torch.profiler (NVIDIA) / 厂商 profiler

层级5: Kernel 级分析
  SM 利用率、显存带宽利用率、register spill、bank conflict
  → ncu (NVIDIA) / 厂商 profiler
```

### 3.2 各层级对应的工具

| 层级 | NVIDIA 工具 | 通用/你们平台 |
|---|---|---|
| 层级1-2 | vLLM 内置统计 | 你们的推理引擎内置统计 |
| 层级3 | NVTX + nsys | 手动 timeit / 打标 |
| 层级4 | torch.profiler | torch.profiler (CPU侧) + 厂商 profiler |
| 层级5 | ncu (Nsight Compute) | 问驱动/编译器同事要 |

### 3.3 实战：nano-vllm profiling

```python
# 层级3: 在 ModelRunner.run_model 中加 NVTX 风格打标
import time

def run_model(self, input_ids, positions, is_prefill):
    stages = {}

    t0 = time.perf_counter()
    if is_prefill or self.enforce_eager or input_ids.size(0) > 512:
        output = self.model.compute_logits(self.model(input_ids, positions))
    else:
        output = ...  # CUDA Graph
    stages['model_forward'] = time.perf_counter() - t0

    # 分别在 prefill 和 decode 时统计
    print(f"{'Prefill' if is_prefill else 'Decode'}: {stages}")
    return output
```

**典型输出**（你会在学习过程中得到这样的数据）：

```

Decode:   model_forward=2.1ms   (访存密集，GPU 等待显存)
```

## 四、第1层：算子级优化

### 4.1 算子融合

| 融合类型 | 融合了什么 | 收益（Decode 阶段） | 对应代码 |
|---|---|---|---|
| RMSNorm + 残差 | add + pow + mean + rsqrt + mul | 少 1 次 kernel launch | nano-vllm `layernorm.py` add_rms_forward |
| SwiGLU gate+up | 两个 Linear 合并为一个 | 少 1 次 matmul kernel | nano-vllm `linear.py` MergedColumnParallelLinear |
| QKV 投影 | 三个 Linear 合并为一个 | 少 2 次 matmul kernel | nano-vllm `linear.py` QKVParallelLinear |
| 逐元素链 | silu + mul | 减少中间 tensor 写回显存 | nano-vllm `activation.py` SiluAndMul |

**为什么 Decode 阶段融合收益大**：

```
Decode 一次 forward:
  无融合:  kernel launch 开销 ≈ 30-50% 总耗时（因为每个 kernel 计算量极小）
  有融合:  kernel launch 次数减半 → 开销降为 15-25%
```

**学习方法**：
1. 读 nano-vllm 每种融合的实现代码
2. 用 nsys / vendor profiler 对比融合前后的 kernel 数量和时间线
3. 思考：**你们的编译器 IR fusion pass 能自动做到哪种程度的融合？哪些需要手写 kernel？**

### 4.2 Tiling — Flash Attention 的精髓

Flash Attention 不单独写文件，直接在你学的 CS336 Chapter 2 hw1 Triton kernel 的基础上理解 tiling 策略：

```
标准 Attention:
  step 1: S = Q@K^T           → 写入 HBM (O(n²) 大小)
  step 2: P = softmax(S)      → 从 HBM 读取 S，写回 P
  step 3: O = P@V             → 从 HBM 读取 P，写回 O
  总 HBM 读写: O(n²)          ← 瓶颈

Flash Attention (Online Softmax + Tiling):
  把 Q 分成多个 tile
  对于每个 Q tile:
    遍历 K, V tile (只在 SRAM 中):
      局部计算 S_tile → online softmax → 累加到 O_tile
  总 HBM 读写: O(n)            ← 减少了一个数量级
```

**与驱动/HAL 的关联**：Tiling 的粒度（tile size）受 SRAM 大小限制，这正是你们 HAL 层需要和编译器约定的硬件参数。

**关键论文**：FlashAttention (Dao et al., 2022) / FlashAttention-2 (Dao, 2023)

## 五、第2层：显存优化

### 5.1 PagedAttention（核心）

这是 vLLM 最重要的创新。传统的 KV Cache 管理方式会导致严重的显存浪费：

```
传统 (Contiguous):
  seq1: [████████████████░░░░░░░░░░░░░░░░]  2000 tokens，预分配 2048，浪费 48
  seq2: [██████████░░░░░░░░░░░░░░░░░░░░░░]  1000 tokens，预分配 2048，浪费 1048
  总浪费: ~50% 显存

PagedAttention (Block-based):
  seq1: [B0][B1][B2][B3][B4]          每个 block = 256 tokens，按需分配
  seq2: [B5][B6]                       用多少分多少
  浪费: ~0%（block 级别）
  额外收益: prefix caching — seq3 共享 B0, B1
```

**已学资源**：nano-vllm [block_manager.py](nano-vllm/nanovllm/engine/block_manager.py)

**重点理解**：
1. `can_allocate()` — 如何检查空闲 block 数量
2. `allocate()` — 分配 block + prefix caching 命中
3. `deallocate()` — 引用计数管理
4. `hash_blocks()` — xxhash 链式哈希

**与 HAL 的关联**：block table 是虚拟地址→物理地址的映射表，类似于操作系统的页表。你们的 HAL 层 KV Cache 管理是否支持类似的分页机制？

**关键论文**：vLLM (Kwon et al., SOSP 2023)

### 5.2 KV Cache 量化

这是一个独立的大话题（见第3层量化），但从显存角度看：

```
28 层 × 2(K,V) × seq_len × num_kv_heads × head_dim × dtype
                                                      ↓
                                              FP16: 2B/token → 全序列 1GB+
                                              INT8: 1B/token → 512MB
                                              INT4: 0.5B/token → 256MB
```

KV Cache 量化 = 直接扩大可用 context length + 减少显存带宽压力。

## 六、第3层：量化优化

### 6.1 量化的三个维度

| 量化目标 | 主要收益 | 难度 | 精度影响 |
|---|---|---|---|
| **Weight-only (W4A16)** | 减少模型文件大小、减少权重的显存带宽 | 低 | 小（GPTQ/AWQ 已成熟） |
| **Weight + Activation (W8A8)** | 矩阵乘用 INT8，加倍吞吐 | 中 | 中（需要校准，SmoothQuant 解决 outlier） |
| **KV Cache (INT8/INT4)** | 减少显存占用、加速 decode | 中 | 中（对 decode 精度敏感） |

### 6.2 量化为什么对 decode 特别重要

回顾 decode 的算术强度 ~3 FLOPs/Byte：

- **降低权重的访存量**（Weight-only 量化）：20% 加速（权重只是访存的一部分）
- **降低 KV Cache 的访存量**（KV Cache 量化）：40-50% 加速（KV Cache 是 decode 的主流访存）
- **两者结合**：可达 2x 加速

### 6.3 推荐学习资源

| 方法 | 论文 | 要点 |
|---|---|---|
| GPTQ | Frantar et al., 2023 | 逐列量化 + Hessian 补偿，W4A16 精度保持 |
| AWQ | Lin et al., 2024 | 按激活值分布选权重重要通道，W4A16 |
| SmoothQuant | Xiao et al., 2023 | 数学等价变换：用 scale 平衡 weight 和 activation 的离群值，W8A8 |
| KV Cache 量化 | 多个工作 | FP8 是工业界主推方向（NVIDIA H100 原生支持） |

**学习方法**：
1. 理解 GPTQ/AWQ 的核心思想（不需要看代码细节）
2. **重点**：理解 SmoothQuant 的数学变换 `Y = (X·diag(s)) · (diag(s⁻¹)·W)` — 为什么不改变结果，却平滑了量化难度
3. 和你们量化团队的同事对一下：你们主推哪种量化方案？

## 七、第4层：调度优化

### 7.1 已学资源回顾

nano-vllm [scheduler.py](nano-vllm/nanovllm/engine/scheduler.py) 已经覆盖了核心调度逻辑，复习时重点看：

1. **Continuous Batching**：running/waiting 队列管理，新请求随时加入
2. **Prefill 优先**：先处理 waiting 中的 prefill，再处理 decode
3. **Chunked Prefill**：大 prompt 分段 prefill，避免阻塞 decode
4. **抢占机制**：显存不够时 preempt → deallocate → 回到 waiting

### 7.2 Prefill / Decode 分离的原因

```
混合调度的问题:
  Prefill (计算密集) + Decode (访存密集) 同时跑
  → GPU 计算单元在 decode 时闲置，显存带宽在 prefill 时闲置
  → 两个都用不满

分离后的优势:
  - 独立调度: prefill 批量到 GPU 利用率高，decode 合并成 batch 提高吞吐
  - Chunked prefill: 长 prompt 分段，不让 decode 等太久
```

### 7.3 关键论文

- Orca (Yu et al., OSDI 2022)：第一个提出 Iteration-Level Scheduling，是 Continuous Batching 的前身
- Sarathi (Agrawal et al., 2023)：提出 chunked prefill，解决 prefill 阻塞 decode 问题

## 八、第5层：图优化

### 8.1 CUDA Graph

nano-vllm [model_runner.py](nano-vllm/nanovllm/engine/model_runner.py) 的 `capture_cudagraph()` 是完整实现。

**原理**：
```
普通执行: CPU for each kernel: launch → wait → launch → wait → ...
CUDA Graph: [capture entire graph once] → replay → 一次提交全部 kernel
```

**为什么只用于 decode**：CUDA Graph 要求 input shape 固定。Decode 的 input 是 `(batch_size, 1)` — batch_size 有限个固定值可预捕获。Prefill 的序列长度千变万化，不能预捕获。

**局限性**（你们自研平台要注意）：
- 不兼容动态 shape
- 不兼容 Python 控制流
- 你们的 NPU 是否支持类似的 graph capture 机制？

### 8.2 torch.compile

已经在 RMSNorm 中学过。它和 CUDA Graph 是互补关系：

| | torch.compile | CUDA Graph |
|---|---|---|
| 优化层面 | **算子融合**（多个小算子 → 1 个大 kernel） | **launch 调度**（多个 kernel → 1 次提交） |
| 粒度 | 单个函数内 | 整个模型 forward |
| 适合阶段 | Prefill + Decode | 仅 Decode |

## 九、第6层：系统级优化

### 9.1 Tensor Parallelism (TP)

nano-vllm [linear.py](nano-vllm/nanovllm/layers/linear.py) 已实现。Review 重点：

```
ColumnParallel:  把权重按列切分到多卡，每卡算一部分输出，无需通信
RowParallel:     把权重按行切分到多卡，输出需要 all-reduce

示例: QKV 投影
  原始: W_qkv 形状 (hidden, 3*hidden)
  TP=2: 每卡持有 (hidden, 1.5*hidden)，输出只含 Q₁ + K₁ + V₁
  无需通信 → 计算完成后自然合并
```

### 9.2 Speculative Decoding（前瞻性解码）

**核心思想**：用一个小模型（草稿模型）快速生成候选 token，用大模型批量验证。

```
传统 Decode:       大模型 → 1 token → 大模型 → 1 token → ...  (串行)
Speculative:  小模型 → 5 tokens → 大模型验证 → 接受 4 个 → 加速 4x
```

这是一种算法级的优化，不改变模型本身。

**关键论文**：SpecInfer (Miao et al., 2023) / Medusa (Cai et al., 2024)

### 9.3 服务化优化

| 优化方向 | 具体做法 |
|---|---|
| 异步处理 | 请求队列 + 异步 callback，不阻塞 API |
| 请求优先级 | 短请求优先（减少平均延迟）、长请求公平调度 |
| 动态批处理 | 根据负载动态调整 batch size |
| 负载均衡 | 多卡/多节点分发，避免单卡过载 |
