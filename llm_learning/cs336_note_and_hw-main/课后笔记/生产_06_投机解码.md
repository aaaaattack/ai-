## 一、问题：Decode 的根本瓶颈

### 1.1 自回归解码的"串行诅咒"

回顾已学的 decode 流程（第9课）：每生成一个 token 要做一次完整的 `model.forward()`，然后采样，再喂回去生成下一个 token。这个过程是严格串行的：

```
t=1: model.forward(token_1)          → output token_2
t=2: model.forward(token_2)          → output token_3
t=3: model.forward(token_3)          → output token_4
...

▶ 每次 forward 只生成 1 个 token → 利用率极低（memory-bound）
▶ GPU/NPU 大部分时间在等数据，计算单元利用率可能不到 10%
```

### 1.2 Speculative Decoding 的核心思想

**用一个快的、小的模型先"猜"几个 token，然后用大模型一次性验证。**

```
不用 SD:  ████████ → token2  ████████ → token3  ████████ → token4
           大模型 forward          大模型 forward       大模型 forward

用 SD:    ████████ → token2,3,4,5 (draft 小模型快速猜 3 个)
          ████████████████ (大模型一次验证 3 个 draft token + 生成 bonus)
```

**本质是一个 trade-off：用 draft 做更便宜的计算换 target 做更少的 forward。**

## 二、核心算法

### 2.1 三步流程

```
┌─────────────┐     ┌──────────────┐     ┌────────────────┐
│  1. Draft   │ →   │  2. Verify   │ →   │  3. Accept/    │
│  小模型快速生成  │     │  大模型一次并行  │     │  Reject     │
│  K 个候选 token │     │  验证 K+1 个    │     │  决定接受几个  │
└─────────────┘     └──────────────┘     └────────────────┘
```

#### Step 1: Draft（生成候选）

Draft 模型（比 Target 小得多）从当前 prefix 开始自回归生成 K 个 token：

```
Target: Qwen3-14B  (14B 参数，~28GB)
Draft:  Qwen3-0.6B (0.6B 参数，~1.2GB)
                              ↑ 小了 23 倍，推理快约 23 倍

Draft 生成: x₁, x₂, ..., x_K   (K = num_speculative_tokens，通常 3~8)
```

#### Step 2: Verify（验证）

Target 大模型一次性吃 `[prefix, x₁, x₂, ..., x_K]`，算出每个位置上的概率分布：

```
p₁ = P(x₁ | prefix)          ← 基于 prefix 的预测，x₁ 的概率
p₂ = P(x₂ | prefix, x₁)      ← 基于 prefix+x₁ 的预测，x₂ 的概率
p₃ = P(x₃ | prefix, x₁, x₂)
...
p_K = P(x_K | prefix, ..., x_{K-1})
p_bonus = P(· | prefix, ..., x_K)   ← bonus token 分布
```

**关键优势：** Target 只做一次 forward，但输入是 K 个 token 拼在一起，可以并行计算所有位置的 output logits。序列长度从 1 变成了 K，decode 的计算密度大幅提高。

#### Step 3: Accept / Reject（接受/拒绝）

这是投机解码最精妙的部分：**如何保证最终输出分布和不用 SD 时完全一致（无损加速）？**

对每个位置 i = 1..K：

```
从 draft 分布 q_i 中采样得到 x_i
计算: p_i(x_i) = target 分布中 x_i 的概率
      q_i(x_i) = draft 分布中 x_i 的概率

生成随机数 u ~ Uniform(0, 1)

if u ≤ p_i(x_i) / q_i(x_i):    接受 x_i，继续下一位置
else:                           拒绝 x_i 及之后所有 draft tokens
                                从修正分布 max(0, p_i - q_i) 中重新采样
                                break
```

**直觉理解：**

```
p_i(x) / q_i(x)  < 1:  target 认为 x 没有 draft 认为的那么"好"   → 可能被拒绝
p_i(x) / q_i(x) >= 1:  target 认为 x 比 draft 认为的还要好        → 一定接受
```

### 2.2 为什么是无损的？

数学证明（简化版）：

最终接受的 token 分布 = p（target 的分布）— 无论 draft 多差都不影响最终输出的数学分布。Draft 更差只会导致更低的接受率，不会导致输出偏差。

**意味着 SD 可以安全使用，不改变模型输出质量 — 只影响速度。**

### 2.3 接受率与加速比

```
假设: K = 5 个 draft token，平均接受率 α = 0.8

每轮 SD 平均产生: 1 + α + α² + α³ + α⁴ = (1 - α⁵) / (1 - α)
               ≈ 1 + 0.8 + 0.64 + 0.51 + 0.41 = 3.36 个 token

代价: 1 次 Target forward + K 次 Draft forward

加速比 ≈ 3.36 / (1 + K × draft_cost_ratio)
  draft_cost_ratio = draft_time / target_time ≈ 1/23 ≈ 0.043 (for 14B+0.6B)

加速比 ≈ 3.36 / (1 + 5×0.043) ≈ 3.36 / 1.22 ≈ 2.75x
```

**关键指标：**
- **Mean Acceptance Length (MAL)**：平均每轮接受多少个 draft token + 1（bonus）
- **Draft Acceptance Rate**：draft token 被接受的比例
- **Per-position Acceptance Rate**：第 0, 1, 2, ... 个位置各自被接受的概率（递减）

HLIEvLLM 的 SD 实现分两层，和之前学的 `ModelRunner` 分离 `BlockManager` + `KVCache` 异曲同工：

```
│  - 复用标准 vLLM Scheduler，零改动                                │
│  - 只是每次 step 时多调一个 spec_decode 路径                      │
└────────────────────────┬────────────────────────────────────────┘

    ┌────────────────────┴────────────────────┐
    │                                         │
    ▼                                         ▼
┌──────────────────────┐           ┌──────────────────────────────┐
│ Proposer 层           │           │ Worker 层                    │
│ vllm/v1/spec_decode/  │           │ vllm/v1/worker/gpu/         │
│                       │           │   spec_decode/               │
│ ┌────────────────────┐│           │ ┌──────────────────────────┐ │
│ │SpecDecodeBase      ││           │ │ EagleSpeculator          │ │
│ │  Proposer          ││  ──→      │ │  - prefill/decode cuda   │ │
│ │  (~1600 行基类)    ││           │ │    graph 管理             │ │
│ │                    ││           │ │  - 多步 decode 循环       │ │
│ │ EagleProposer      ││           │ └──────────────────────────┘ │

└──────────────────────┘
```

**Proposer 层**：负责"怎么猜 draft tokens"（策略）
**Worker 层**：负责"怎么执行 draft model forward"和"怎么做 rejection sampling"（执行）

## 四、五种 Draft 策略详解

### 4.1 Draft Model（独立草稿模型）

[`vllm/v1/spec_decode/draft_model.py`](file:///e:/cs336_note_and_hw-main/cs336_note_and_hw-main/HLIEvLLM-1.4.0rc0/vllm/v1/spec_decode/draft_model.py)

最直观的方法：用一个独立的小模型作为 draft。

```python
class DraftModelProposer(SpecDecodeBaseProposer):
    def __init__(self, vllm_config, device, runner=None):
        super().__init__(
            vllm_config=vllm_config,
            device=device,
            pass_hidden_states_to_model=False,  # ← Draft model 有独立参数
            runner=runner,
        )
```

**特点：**
- Draft model 是一个独立的小模型（如 TinyLlama-1.1B、Qwen3-0.6B）
- 必须和目标模型共享相同的 tokenizer vocab
- TP size 必须一致（否则 torch compile cache 冲突）
- 优点是简单直接，缺点是需要额外显存

### 4.2 EAGLE（特征级别投机）

[`vllm/v1/spec_decode/eagle.py`](file:///e:/cs336_note_and_hw-main/cs336_note_and_hw-main/HLIEvLLM-1.4.0rc0/vllm/v1/spec_decode/eagle.py)

```python
class EagleProposer(SpecDecodeBaseProposer):
    def __init__(self, vllm_config, device, runner=None):
        super().__init__(
            vllm_config, device,
            pass_hidden_states_to_model=True,  # ← 传入 target 的 hidden states！
            runner=runner,
        )
```

**核心创新：** Draft 不需要 embedding + 完整前向 — 直接用 Target 的 hidden states 作为输入。

```
正常 decode:      target 跑完 N 层 → hidden_states → lm_head → logits → token
EAGLE draft:      target 跑完 N 层 → hidden_states
                          ↓
                  EAGLE head (一个小网络，~一层 Transformer)
                          ↓
                  lm_head (共享 target 的) → logits → draft token

优势：
  1. 共享 lm_head 和 embedding，大幅省显存
  2. 利用 target 已经算好的 hidden states，零成本"特征提取"
  3. EAGLE head 通常只有 1 层 Transformer ~ 几十 MB
```

**EAGLE3** 在此基础上增加了 aux hidden states（利用前一层 target 的 hidden states），提升接受率。

### 4.3 Medusa（多头预测）

Medusa 在 target 模型上附加多个预测头（每个头预测未来第 1, 2, ..., K 个 token），一次 forward 直接生成所有 draft tokens。

```
Model forward  →  hidden_states
                      ├── Medusa Head 1 → 预测下一个 token
                      ├── Medusa Head 2 → 预测下下个 token
                      └── Medusa Head K → 预测第 K 个 token

一次 forward 直接出 K 个 draft tokens（不需要自回归循环）
```

### 4.4 N-gram（无模型模式）

[`vllm/v1/spec_decode/ngram_proposer.py`](file:///e:/cs336_note_and_hw-main/cs336_note_and_hw-main/HLIEvLLM-1.4.0rc0/vllm/v1/spec_decode/ngram_proposer.py)

**不需要任何额外模型**，完全基于文本匹配。

```python
class NgramProposer:
    def __init__(self, vllm_config):
        self.min_n = ...  # 最小匹配长度
        self.max_n = ...  # 最大匹配长度
        self.k = ...      # num_speculative_tokens
```

**算法：** 在已经生成的文本（包括 prompt）中查找最近出现的 N-gram，用匹配位置后面的 token 作为 draft：

```
Prompt: "The capital of China is Beijing. The capital of Japan is Tokyo. The capital of"
查找: "The capital of" → 匹配! → draft: ["China", "is", "Beijing"] 
     （或者更近的: "Japan", "is", "Tokyo"] — 取决于匹配策略）
```

**特点：**
- 零额外显存，纯 CPU 端 Numba JIT 计算
- 对重复性强的任务效果好（代码生成、翻译）
- 对创意性任务效果差（文本没有明显的 N-gram 模式）

### 4.5 MTP（Multi-Token Prediction）

[`vllm/config/speculative.py`](file:///e:/cs336_note_and_hw-main/cs336_note_and_hw-main/HLIEvLLM-1.4.0rc0/vllm/config/speculative.py#L34-L53)

```python
MTPModelTypes = Literal[
    "deepseek_mtp", "mimo_mtp", "glm4_moe_mtp", "ernie_mtp",
    "nemotron_h_mtp", "exaone_moe_mtp", "qwen3_next_mtp",
    "qwen3_5_mtp", "longcat_flash_mtp", "gemma4_mtp", ...
```

**MTP 是"内建"在目标模型里的 SD：** 训练时就在 target 模型里加了额外的预测头，推理时直接输出 K 个 future token。

与 EAGLE 的区别：EAGLE 是**事后训练**一个 head，MTP 是**训练时就一起训**。

## 五、Draft Proposal 核心代码

### 5.1 `propose()` — 最核心的方法

[`vllm/v1/spec_decode/llm_base_proposer.py`](file:///e:/cs336_note_and_hw-main/cs336_note_and_hw-main/HLIEvLLM-1.4.0rc0/vllm/v1/spec_decode/llm_base_proposer.py#L392-L592)

```python
def propose(
    self,
    target_token_ids,       # Target 模型上次输出的 token IDs [num_tokens]
    target_positions,       # 对应的位置 [num_tokens]
    target_hidden_states,   # Target 模型的 hidden states [num_tokens, hidden_size]
    next_token_ids,         # 每个请求的下一个 token [batch_size]
    common_attn_metadata,   # Attention 元数据
    sampling_metadata,      # 采样元数据
) -> torch.Tensor:
    # 返回: [batch_size, num_speculative_tokens] 的 draft token IDs

    # === 1. 第一轮：用 target hidden states + next_token_ids 跑 draft model ===
    num_tokens, token_indices_to_sample, common_attn_metadata = (
        self.set_inputs_first_pass(...)
    )
    
    # 跑 draft model 前向
    ret_hidden_states = self.model(**model_kwargs)
    last_hidden_states, hidden_states = ret_hidden_states
    
    # 采样 → 第一个 draft token
    sample_hidden_states = last_hidden_states[token_indices_to_sample]
    draft_token_ids = self._greedy_sample(sample_hidden_states)
    
    # === 2. 后续 K-1 轮：自回归生成剩余 draft tokens ===
    draft_token_ids_list = [draft_token_ids]
    
    for token_index in range(self.num_speculative_tokens - 1):
        # 更新位置、slot_mapping、seq_lens
        positions = self._update_positions_dependent_metadata(...)
        
        # 输入: 当前 draft token + 上一步的 hidden states
        self.input_ids[:batch_size] = draft_token_ids_list[-1].int()
        self.hidden_states[:batch_size] = hidden_states
        
        # 跑 draft model
        ret_hidden_states = self.model(**model_kwargs)
        
        # 采样 → 下一个 draft token
        draft_token_ids = self._greedy_sample(last_hidden_states[:batch_size])
        draft_token_ids_list.append(draft_token_ids)
    
    # [batch_size, num_speculative_tokens]
    return torch.stack(draft_token_ids_list, dim=1)
```

**流程可视化：**

```
                Target hidden_states
                        │
                        ▼
        ┌──────────────────────────────┐
        │ Draft Model Forward (step 0) │
        │ 输入: token_ids, positions,  │
        │       hidden_states          │
        │ 输出: draft_token_1, new_hs  │
        └──────────────┬───────────────┘
                       │
        ┌──────────────▼───────────────┐
        │ Draft Model Forward (step 1) │
        │ 输入: draft_token_1, new_hs  │
        │ 输出: draft_token_2, new_hs  │
        └──────────────┬───────────────┘
                       │
                      ...
                       │
        ┌──────────────▼───────────────┐
        │ Draft Model Forward (step K-1)│
        │ 输出: draft_token_K          │
        └──────────────────────────────┘

最终输出: [draft_token_1, draft_token_2, ..., draft_token_K]
                                                          (batch_size × K)
```

### 5.2 Target 模型验证

Draft tokens 生成后，Target 模型一次性吃 `[prefix_tokens, draft_token_1, ..., draft_token_K]`（batch expansion）：

```
原来的 batch = [seq1, seq2, ..., seqB]  共 B 个请求
batch expansion 后 = B × (K + 1) 个 token

原本 decode 每次 forward 只算 B 个 token（每个请求 1 个）
现在是 B × (K + 1) 个 token → compute/memory ratio 提高 (K+1) 倍
```

### 6.1 `RejectionSampler`

[`vllm/v1/worker/gpu/spec_decode/rejection_sampler.py`](file:///e:/cs336_note_and_hw-main/cs336_note_and_hw-main/HLIEvLLM-1.4.0rc0/vllm/v1/worker/gpu/spec_decode/rejection_sampler.py#L40-L143)

```python
class RejectionSampler:
    def __init__(self, sampler, spec_config, device):
        self.num_speculative_steps = spec_config.num_speculative_tokens
        self.rejection_sample_method = spec_config.rejection_sample_method

    def __call__(self, logits, input_batch, draft_logits=None):
        # 1. 先应用 sampling params（temperature, top-k, top-p, penalties）
        processed_logits = self.sampler.apply_sampling_params(logits, ...)
        
        # 2. 调用 Triton kernel 做 rejection sampling
        sampled, num_sampled = rejection_sample(
            processed_logits,    # Target 的 logits [sum(K+1), V]
            draft_logits,        # Draft 的 logits (可选，仅 draft_model 模式下有)
            draft_sampled,       # Draft 采样出的 token IDs
            cu_num_logits,       # 每个请求的 logits 数量前缀和
            pos,                 # 位置信息
            idx_mapping,         # 请求索引映射
            temperature,
            seeds,
            self.num_speculative_steps,
            self.synthetic_conditional_rates,  # 可选：合成接受率
        )
        
        # sampled: [batch_size × (K+1)] 实际接受的 token IDs
        # num_sampled: [batch_size] 每个请求接受了几个
        return SamplerOutput(sampled_token_ids=sampled, num_sampled=num_sampled)
```

### 6.2 Triton Kernel 中的 Accept/Reject 逻辑

[`vllm/v1/worker/gpu/spec_decode/rejection_sampler_utils.py`](file:///e:/cs336_note_and_hw-main/cs336_note_and_hw-main/HLIEvLLM-1.4.0rc0/vllm/v1/worker/gpu/spec_decode/rejection_sampler_utils.py)

```python
@triton.jit
def _compute_block_stats_kernel(...):
    """
    在 GPU 上并行计算每个 draft token 对应的 target 和 draft 的 
    logit max/sumexp，准备 rejection sampling
    
    关键计算:
    - target_local_max/argmax/sumexp
    - draft_local_max/sumexp  (如果有 draft logits)
    """
```

**Rejection 判断逻辑（Triton 实现）**：

```python
# 伪代码
for each position i in [0, K-1]:
    # 1. 从 draft 分布采样 → x_i
    draft_token = sample_from(draft_distribution)
    
    # 2. 计算接受概率
    p = target_distribution[draft_token]    # target 模型认为这个 token 的概率
    q = draft_distribution[draft_token]     # draft 模型认为这个 token 的概率
    
    # 3. 随机接受/拒绝
    u = random()  # Uniform(0, 1)
    if u <= p / q:  # 接受
        accept(draft_token)
        continue      # 继续检查下一个 draft token
    else:             # 拒绝
        # 修正分布: re-softmax max(0, p - q)
        resample_from(max(0, target_dist - draft_dist))
        break         # 拒绝后不再检查后续 draft token

# 4. Bonus token: 从最后一个接受位置的 target distribution 中采样
bonus_token = sample_from(target_distribution)
```

## 八、Houmo 的投机解码实现

Houmo 采用了最直接的方式：**Draft Model**（独立编译 draft .hmm），配合 TCIM Runtime 实现。

### 8.1 模型结构

[`houmo-examples-xh2/apis/inferences/qwen3_speculative/README.md`](file:///e:/cs336_note_and_hw-main/cs336_note_and_hw-main/houmo-examples-xh2/apis/inferences/qwen3_speculative/README.md)

```
qwen3/output/xh2/
├── qwen3-speculative-0.6b_prefill_draft.hmm   # Draft Prefill (0.6B)
├── qwen3-speculative-0.6b_decode_draft.hmm    # Draft Decode (0.6B)
├── qwen3-speculative-14b_prefill.hmm          # Target Prefill (14B)
└── qwen3-speculative-14b_verify.hmm           # Target Verify (14B)
```

**四个 .hmm 文件的角色：**

| 文件 | 角色 | 大小 | 用途 |
|---|---|---|---|
| `0.6b_prefill_draft` | Draft prefill | ~1.2GB | 接收 prompt + hidden state，算 KV Cache |
| `0.6b_decode_draft` | Draft decode | ~1.2GB | 自回归生成 K 个 draft token |
| `14b_prefill` | Target prefill | ~28GB | 接收原始 prompt，算 KV Cache |
| `14b_verify` | Target verify | ~28GB | 一次性验证 K 个 draft token + 生成 bonus |

### 8.2 运行时流程

[`houmo-examples-xh2/apis/inferences/qwen3_speculative/demo.py`](file:///e:/cs336_note_and_hw-main/cs336_note_and_hw-main/houmo-examples-xh2/apis/inferences/qwen3_speculative/demo.py#L490-L600)

```python
class QwenSpeculative:
    def classic_mode(self, next_id, temperature=0.6, top_k=1, top_p=0):
        draft_ids = []
        draft_logits = []
        
        while True:
            # ====== Phase 1: Draft 自回归生成 K 个候选 token ======
            draft_ids.append(next_id)
            for i in range(self.max_step - 1):
                output_data = self._run_decode(next_id)    # 0.6B decode
                next_id = output_data.argmax(-1)[0]
                draft_ids.append(next_id)
                draft_logits.append(output_data)            # 保留 logits 用于 rejection
            
            # ====== Phase 2: Target 一次性验证 ======
            verify_output_data = self._run_verify(draft_ids)  # 14B verify
            verified_ids = np.argmax(verify_output_data, axis=2).flatten()
            
            # ====== Phase 3: Rejection Sampling ======
            for i in range(self.step - 1):
                draft_logit = torch.tensor(draft_logits[i][0][0])
                verify_logit = torch.tensor(verify_output_data[0][i])
                
                # Apply temperature / top-k / top-p
                draft_distrib = norm_logits(draft_logit, temperature, top_k, top_p)
                verify_distrib = norm_logits(verify_logit, temperature, top_k, top_p)
                
                # Sample from draft
                draft_id = sample(draft_distrib)
                p = verify_distrib[draft_id]        # target prob of draft token
                q = draft_distrib[draft_id]         # draft prob of draft token
                u = np.random.rand(1)[0]
                
                if p < q and u > (p / q):           # reject
                    new_verify = torch.maximum(
                        torch.zeros_like(verify_distrib),
                        verify_distrib - draft_distrib
                    )
                    new_verify = new_verify / new_verify.sum()
                    next_id = sample(new_verify)    # re-sample from corrected dist
                    is_accept_all = False
                    break
                else:                                # accept
                    next_id = draft_id
```

### 8.3 Verify 模型

[`houmo-examples-xh2/apis/inferences/qwen3_speculative/demo.py`](file:///e:/cs336_note_and_hw-main/cs336_note_and_hw-main/houmo-examples-xh2/apis/inferences/qwen3_speculative/demo.py#L440-L471)

```python
def _run_verify(self, draft_ids):
    """Target 模型一次前向验证 K 个 draft tokens"""
    # 拼接 K 个 draft token 的 embedding
    ids_embedding = []
    for id in draft_ids:
        id_embedding = F.embedding(id.unsqueeze(0), self.verify_embedding_weight)
        ids_embedding.append(id_embedding)
    # → [1, K, hidden_dim]
    verify_input_data = torch.stack(ids_embedding, dim=0).squeeze().unsqueeze(0)
    
    # Pad 到固定 max_step
    padding_needed = self.verify_max_step - self.step
    verify_input_data = F.pad(verify_input_data, (0, 0, 0, padding_needed, 0, 0))
    
    self.verify.set_input(...)
    self.verify.run()
    self.verify.sync()
    
    return verify_output_data  # [1, K, vocab_size]
```

**关键：** Verify 模型是编译时固定了 shape 的，pad 到 `verify_max_step`（相当于 `num_speculative_tokens`）。这又是一个静态图适配动态场景的典型案例。

## 九、不同方法对比

| 方法 | 需要额外模型 | 额外显存 | 接受率 | 适用场景 |
|---|---|---|---|---|
| **N-gram** | 无 | 0 | 低~中 | 代码生成、翻译、结构化文本 |
| **Draft Model** | 独立小模型 | ~1-2GB | 中~高 | 通用，任何有 vocab 兼容小模型的情况 |
| **EAGLE** | 小 head 网络 | ~50-200MB | 高 | 通用，有 EAGLE head 的模型 |
| **EAGLE3** | 小 head 网络 | ~50-200MB | 更高 | EAGLE 的增强版 |
| **Medusa** | 多头 | ~100-500MB | 中~高 | 通用 |
| **MTP** | 内建 | 0（训练时已有） | 高 | 原生支持 MTP 的模型（DeepSeek、Qwen3-Next 等） |
| **Suffix** | 无 | 0 | 中 | 后缀匹配（类似 N-gram） |

## 十、与推理工具链工作的关联

| 关联方向 | 具体场景 |
|---|---|
| **编译器团队** | Draft 模型也是 .hmm 编译产物 → 同样需要 `prefill` + `decode` 两套图；Verify 模型需要支持 batch expansion（输入 K 个 token 而非 1 个） |
| **量化团队** | Draft 模型可以做 INT4/FP8 量化进一步缩小 → 让 draft 更快；Verify 模型也可以做 W8A8 → 提升 compute/memory ratio |
| **Runtime/驱动** | Houmo 当前是两套独立流程（draft prefill/decode + target verify），需要 Hardware DMA Assembly 协调两套模型的 KV Cache 传递 |
| **性能优化** | 接受率是最核心的指标 → 接受率每提升 10%，吞吐量可能提升 20-30%（非线性）；需要关注 per-position acceptance rate 的衰减曲线 |
| **客户方案** | "怎么让推理更快"的终极答案之一——如果客户场景是重复性强的内容（客服、翻译、代码生成），N-gram 甚至不需要额外模型就能获得 2x 加速 |

## 十一、白话总结

```
Speculative Decoding = "猜词 + 验证"

就像做选择题:
  - 普通做法: 一道一道做，做一道对一道答案
  - SD 做法:  先快速把 5 道题的答案都写上（draft），然后翻答案（verify）
              答对的保留，答错的擦掉重做

Draft = 草稿纸上的快速涂鸦
Verify = 对照标准答案逐字检查
Reject = 发现写错了 → 擦掉重写（无损，保证最终答案和逐字写一样）

加速原理：
  大模型一次验证 K 个 token 的时间 ≈ 生成 1 个 token 的时间
  小模型生成 K 个 token 的时间 ≈ 0.1 × 大模型生成 1 个 token 的时间
  所以: 总时间 ≈ 1.1 × 单 token 时间 → 产出 1+K×acceptance_rate 个 token
  
  K=5, acceptance=0.7: 产出 4.5 token / 耗时 1.1 → 加速 ~4x
  K=5, acceptance=0.5: 产出 3.5 token / 耗时 1.1 → 加速 ~3.2x
```

## 十二、思考题

1. **为什么 EAGLE 的接受率通常高于 Draft Model？**
   - 提示：EAGLE 用了 target 的 hidden states 作为输入，draft model 从零开始

2. **N-gram 方法在什么场景下接受率高？什么时候会很低？**
   - 提示：代码生成 vs 创意写作，prompt 中是否有足够的 N-gram 模式

3. **Houmo 的 verify 模型为什么需要 pad 到固定 max_step？这和之前学的静态图限制有什么关系？**
   - 提示：.hmm 编译时 shape 固定，但 SD 中实际 draft 数量可能小于 max_step（提前拒绝）

4. **如果 draft model 只有 0.1% 的目标模型大小，接受率可能很低。这时 SD 还有加速效果吗？**
   - 提示：计算 draft_cost_ratio 和 acceptance_rate 的 trade-off
   - 极端情况：draft 只有 0.001% cost 但 acceptance 只有 0.1 → 还有效吗？

5. **为什么 TP 多卡时 Draft Model 的 TP size 必须和 Target 一致？**
   - 提示：看看 `_raise_if_draft_tp_mismatch` 方法的注释（torch compile cache 冲突）
