# Houmo 编译器学习路径

> 基于当前工程 `houmo-examples-xh2` 和 `HLIEvLLM-1.4.0rc0` 的编译器相关代码分析
> 目标：作为解决方案工程师，能读懂编译流水线、能定位问题、能与编译器团队有效沟通

---

## 一、为什么学编译器（优先级排序）

| 优先级 | 原因 | 举例 |
|--------|------|------|
| 1 | **编译是推理链路的入口** — 模型 → `.hmm` (编译器产出) → TCIM Runtime → HAL → NPU。理解编译才能理解全流程 | 客户问"为什么这个模型编译失败"，你需要知道是前端 trace 失败、还是 ONNX 导出失败、还是后端映射失败 |
| 2 | **编译器是你工作的核心瓶颈** — 天天跟编译器团队打交道 | 客户问题绕不开编译环节 |
| 3 | **已学完量化** — 作为方案工程师，5 课量化（INT8/FP8 基础 + GPTQ/AWQ/SmoothQuant/KV Cache 量化）已经够用，再深入是量化团队的事 |

## 三、当前工程中的编译器相关代码

### 3.1 Houmo/XH2 编译管线全貌

```
HuggingFace Model (PyTorch)
    │
    ▼  [xh_model_merak wrap_model]              ← TorchFX 前端
XHModel (Wrapped pytorch model)
    │
    ▼  [to_frontend_graph / TorchFX]             ← 前端图构建
Frontend Graph (Torch FX Graph)
    │
    ▼  [to_quant_graph + ptq_quantize]           ← 量化
Quantized Graph (XHQuantedGraph)
    │
    ▼  [to_export_graph + to_export_hmonnx_v2]   ← HMONNX 导出
HMONNX (ONNX-like IR with quant params)
    │
    ▼  [hmatc ONNX optimizer passes]             ← ONNX 图优化
    │    - onnxGeneralOptimizer (替换/融合/删除)
    │    - onnxXh2Optimizer (芯片特定优化)
    │
    ▼  [tcim.builder.api.build_from_hmonnx]      ← 编译器后端
    │    - MLIR 编译 (skip_mlir_compile 参数)
    │    - 算子映射到芯片指令
    │
    ▼
HMM File (.hmm, 芯片可执行格式)
    │
    ▼  [tcim_lite.runtime.load/run]              ← 芯片推理
Inference on XH2 Hardware
```

### 3.2 各层级文件清单

| 层级 | 目录 | 核心文件数 | 是否可读 | 作用 |
|------|------|-----------|----------|------|
| 编译入口 | `models/llm/*/build.py` (30+ 个模型) | ~30 | ✅ 易读 | 一键编译 + 精度验证 |
| 编译前端 Merak | `hmodel/xh2/xhmodel_merak/xh_llm/` | ~20 | ✅ 核心 | HF 模型 → TorchFX → HMONNX |
| ONNX 图优化 | `hmatc/hmatc/optimizer/` | ~20 | ✅ 可读 | 通用 ONNX 优化 + XH2 芯片优化 |
| PTQ 量化 | `models/llm/*/ptq.py` (10+ 个模型) | ~10 | ✅ 可读 | QuaRot + GPTQ 量化脚本 |
| TCIM Runtime | `houmo_tcim_runtime_xh2_*/` | ~5 | ⚠️ 仅 API | 运行时加载 .hmm + 推理 |
| HMM 工具链 | `tools/hm_check/` + `bin/readhmm` | ~5 | ⚠️ 二进制 | 读取/检查/精简 .hmm 文件 |

## 九、光看 Houmo 代码不够——需要补的理论基础

### 9.1 从 Houmo 代码能学到什么

| 能学到 | 从哪学 |
|--------|--------|
| 完整的 ML 编译流水线长什么样 | `base_model.py` 状态机 |
| ONNX 图优化有哪些常见 Pass | hmatc optimizer 的融合/替换/消除规则 |
| 量化如何嵌入编译流水线 | PTQ 脚本 + `to_quanted_aligned()` |
| Prefill/Decode 为什么分开编译 | `base_llm_model.py` 的双图导出 |
| 芯片特有的融合模式有哪些 | `onnxXh2FusionFunctions.py` |

### 9.2 只看代码学不到什么

| 知识盲区 | 为什么重要 | 推荐资源 | 建议用时 |
|----------|-----------|----------|----------|
| **Torch FX 的工作机制** | Merak 管线的核心是 `torch.fx` trace。不懂 symbolic_trace / GraphModule / Node 类型，就看不懂前端怎么把 HF 模型变成图 | [PyTorch FX 官方教程](https://pytorch.org/docs/stable/fx.html) | 1 小时 |
| **ONNX 协议与算子语义** | HMONNX 是 ONNX 的变体。需要了解 Node/Graph/Tensor/Attribute 结构 | [ONNX IR 规范](https://onnx.ai/onnx/intro/concepts.html) | 30 分钟 |
| **MLIR 的基本概念** | TCIM 后端使用 MLIR。需要理解 Dialect/Pass/Conversion 的概念 | [MLIR Toy Tutorial](https://mlir.llvm.org/docs/Tutorials/Toy/) | 1 小时 |
| **ML 编译器全景** | 建立对"编译器在 ML 系统中做什么"的整体认知 | [The Deep Learning Compiler Survey (Li et al., 2020)](https://arxiv.org/abs/2002.03794) | 1-2 小时 |
| **计算图 IR 的表示形式** | 不理解 SSA/数据流图/DAG，就看不懂为什么某些 Pass 要那样做 | 看一个简单教程即可，不需要读《编译原理》（龙书） | — |
| **图遍历与模式匹配** | 融合 Pass 的本质是"在图中找特定子图模式然后替换" | PyTorch FX 的 `subgraph_rewriter` 文档 | — |

### 9.3 建议按需看的资料

| 资料 | 什么时候看 |
|------|-----------|
| **TVM "Bring Your Own Codegen" 教程** | 想理解 "从图到芯片指令" 这一步做了什么 |
| **MLIR Toy Tutorial** | TCIM 后端 MLIR 报错时能看懂 |
| **XLA 的 HLO 文档** | 对比理解 Google 的编译管线设计思路 |
| **IREE 项目文档** | MLIR-based 推理编译器的另一个参考实现 |

### 9.4 不需要看的

- 《编译原理》（龙书）— 太重，面向通用编程语言而不是 ML 图
- LLVM 深度源码 — Houmo 不基于 LLVM
- GCC/Clang 源码 — 完全不相关

## 十、务实的学习策略

> 核心原则：**不要提前学完所有理论再去看代码，而是看代码遇到不懂的再针对性补理论。**

### 代码驱动的按需学习

```
学习 Merak 管线:
  遇到 torch.fx.symbolic_trace → 花 1 小时看 FX 教程
  遇到 torch.fx.Node 的操作 → 对照 FX 文档查 API
  遇到 ONNX attribute 读写 → 对照 ONNX IR 规范查字段定义
  
学习 hmatc Optimizer:
  遇到 Pattern 匹配规则 → 理解一下 subgraph matching 的概念
  遇到融合函数 → 画一下融合前后的图，理解等价的数学条件
  
学习 TCIM 后端:
  遇到 MLIR 报错 → 花 30 分钟看 MLIR Toy Tutorial 理解 dialect/pass 概念
  遇到算子不支持 → 和编译器团队确认支持矩阵
```

### 你的定位

| 角色 | 需要的能力 |
|------|-----------|
| 解决方案工程师（你） | **能看懂编译流水线 + 能定位问题** |
| 编译器开发工程师 | 能写融合规则、能实现新 Pass、能优化后端 |
| 量化算法工程师 | 能设计量化方案、能调 calibration 参数 |

你不需要"能写一个编译器"，但需要"客户问为什么编译失败时，你能准确告诉编译器团队故障出现在哪一步"。

## 十一、闭源代码学习指南（TCIM Builder 编译器后端）

> 你有机会看到 TCIM 编译器后端的闭源代码。这是整个编译管线最有价值但也最难啃的部分。
> 关键是要有正确的预期和学习策略——你不是去"读懂每一行"，而是去"建立系统级的理解"。

### 11.1 闭源代码里大概有什么

根据 Houmo 开源代码中 `build_from_hmonnx()` 的调用方式、编译参数（`flash_attention`, `llm_opt`, `skip_mlir_compile`）、编译日志输出以及业界 NPU 编译器的通用架构，闭源代码大概率包含以下层次：

```
HMONNX (.onnx)
    │
    ▼
┌─────────────────────────────────────────────────────┐
│  层 1: IR 导入与转换                                  │
│  - ONNX Graph → MLIR 的 TCIM High-Level Dialect       │
│  - 算子分解：复合 ONNX op → 基础 NPU op                 │
│  - 类型系统转换（动态 shape → 静态 shape）               │
└──────────────────────────┬──────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────┐
│  层 2: 图级优化 (MLIR Passes)                        │
│  - 算子融合（NPU 特有：注意 + 量化 + GEMM 融合等）      │
│  - 数据布局变换（NCHW → NPU 内部布局）                  │
│  - 常量折叠 / 死代码消除                                │
│  - 内存规划（buffer 分配 / 复用 / 生命周期分析）         │
│  - 子图切分（哪些在 NPU 跑，哪些回退 CPU）              │
└──────────────────────────┬──────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────┐
│  层 3: Lowering（高层 IR → 低层 IR）                 │
│  - High-Level Dialect → Low-Level NPU Dialect        │
│  - 算子 Lowering：tcim.matmul → npu.mac_instruction   │
│  - Tiling 决策：大矩阵拆成多大一块                       │
│  - 精度选择：fp16 / fp8 / int8 的硬件指令映射            │
└──────────────────────────┬──────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────┐
│  层 4: 后端代码生成                                    │
│  - 指令调度（NPU 指令的顺序编排）                       │
│  - 寄存器分配                                           │
│  - 权重数据布局转换（weight layout transformation）     │
│  - DMA 传输规划（DDR ↔ 片上 SRAM 的数据搬运）           │
│  - 同步屏障插入（barrier / fence）                      │
└──────────────────────────┬──────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────┐
│  层 5: 序列化与打包                                    │
│  - 二进制指令编码 → HMM 文件格式                        │
│  - 权重数据序列化                                       │
│  - 元信息嵌入（tensor shape / dtype / memory layout）    │
│  - 调试符号（可选，由 hmmstrip 移除）                    │
└──────────────────────────┬──────────────────────────┘
                           │
                           ▼
                       HMM File
```

### 11.2 你不需要读懂全部——分级学习目标

**Level 1（必须掌握）**：能看懂编译日志、能定位问题属于哪一层

```
编译日志中的典型错误信息                   → 对应层

"unsupported op: xxx"                   → 层 1: 算子不支持
"shape inference failed"                → 层 1: 动态 shape 无法静态化
"memory allocation failed / OOM"        → 层 2: 内存规划失败
"tiling config not found for shape xxx" → 层 3: Tiling 策略不覆盖
"instruction encoding error"            → 层 4: 指令生成失败
"failed to serialize"                   → 层 5: HMM 打包失败
```

> 这是你作为方案工程师最核心的能力——客户问"为什么编译失败"，你能一分钟定位到是哪一层的问题，并把准确信息转给编译器团队。

**Level 2（建议掌握）**：理解各层的关键设计决策

| 层 | 关键设计决策 | 对客户的影响 |
|----|------------|------------|
| 层 1 | 支持哪些 ONNX op？哪些需要拆解？ | 客户模型能不能编译 |
| 层 2 | 什么条件下触发融合？融合后精度如何？ | 编译后精度是否下降 |
| 层 3 | Tiling 策略如何影响性能和显存？ | 大模型能不能跑（OOM 往往跟 tiling 有关） |
| 层 4 | 是否支持 FP8 指令？权重布局转换有没有精度损失？ | 量化模型能不能用 |

**Level 3（可选深入）**：理解具体算法实现

- 内存规划算法（贪心分配？图着色？）
- Tiling 决策算法（启发式搜索？cost model？）
- 指令调度算法（list scheduling？software pipelining？）

> 这层是编译器开发的事，你作为方案工程师不需要掌握，但知道"用了什么算法"有助于和编译器团队深入讨论。

### 11.3 如何分步骤阅读闭源代码

```
第一步：先不读代码，先读编译日志
  - 找一个成功编译的案例（如 Qwen3-0.6B）
  - 从头到尾读编译日志
  - 标注日志中每一行的含义：
    "IR import begin"            → 层 1 开始
    "Graph optimization pass 1"  → 层 2 某个 Pass
    "Lowering to NPU dialect"    → 层 3 开始
    "Instruction scheduling"     → 层 4 开始
    "Serializing to HMM"         → 层 5 开始
  - 这给你一张"地图"，知道闭源代码的入口和出口是什么函数

第二步：沿着一个简单模型的编译调用链走一遍
  - 选最简单的模型（如一个单层 MLP 或 ResNet block）
  - 从 build_from_hmonnx() 入口开始
  - 用 grep/IDE 跳转跟着调用链走：看每一层的主入口函数
  - 不需要读函数内部实现，只需理解：
    这个函数的输入是什么 IR 格式？
    这个函数的输出是什么 IR 格式？
    变换的核心逻辑是什么（函数名 + 注释就够）？

第三步：逐层深入感兴趣的部分
  - 层 2（图优化）和层 3（Tiling）对解决问题最有用
  - 看几个具体的 Pass 实现：

  - 把常见错误码 → 对应层 → 相关代码位置 整理成表
```

### 11.4 看闭源代码前的理论准备（排序）

| 优先级 | 理论 | 为什么 | 不看会怎样 |

| **必看** | MLIR 官方文档的 Pass Infrastructure 章节 | 理解 Pass 的注册、调度、依赖管理 | 不知道为什么这些 Pass 按这个顺序跑 |

### 11.5 从 API 入口反推的阅读起点

从开源的 `build_from_hmonnx()` 调用处，你已经知道：

```python
# 开源的调用点
tcim.builder.api.build_from_hmonnx(
    hmonnx_path="./hmquant_qwen3/prefill_0.onnx",
    output_dir="./output/",
    compile_config=CompileConfig(
        flash_attention=True,    # → 层 2/3: 特殊处理 FlashAttention
        llm_opt=True,            # → 层 2: LLM 专属优化
        skip_mlir_compile=False, # → 跳过某些 MLIR Pass
        chip_arch="xh2",         # → 层 3/4: 芯片型号决定指令集
        tensor_parallel=1,       # → 层 2: TP 切分策略
    )

```

**进闭源代码后先找这些参数对应的处理逻辑**：
- `flash_attention=True` → 搜索 "FlashAttention" 或 "FA"，看它触发了哪些融合规则
- `llm_opt=True` → 搜索 "llm_opt"，看 LLM 特殊优化是什么（大概率是 KV Cache 相关的内存优化）
- `chip_arch="xh2"` → 搜索 "xh2"，看芯片特定的 Lowering 和指令编码
- 编译报错时 → 搜索报错字符串，反向追踪是哪个 Pass 抛出的

### 11.6 学习周期建议

```
准备阶段（半天）：
  - 看 MLIR Toy Tutorial Ch1-4 → 建立 MLIR 基本认知
  - 找一个成功案例，通读编译日志 → 建立"地图"

第一阶段（1-2 天）：宏观理解
  - 找到每层的主入口函数
  - 整理出完整的调用链（函数调用关系图）
  - 不深入实现细节

第二阶段（2-3 天）：选择性深入
  - 层 2（图优化）挑 2-3 个 Pass 看实现
  - 层 3（Lowering）看 1 个算子的 Lowering 全过程
  - 层 4（代码生成）了解指令编码格式

第三阶段（持续）：积累速查表
  - 每遇到一个新错误，补充到速查表
  - 逐步积累对编译器行为的直觉
```

### 11.7 关键提醒

1. **闭源代码可能非常大**（几万到几十万行）。不要试图全部读完——你没有这个时间，也没有这个必要。

2. **MLIR 代码的阅读体验不同于普通 C++**。TableGen 定义的 Dialect/Op 和 C++ 实现的 Pass 是分开的。先看 TableGen 定义（理解有什么算子），再看 Pass 实现（理解做了什么变换）。

3. **善用编译日志定位代码**。编译日志中的每一行通常对应代码中的一个 Pass 或一个处理步骤。grep 日志中的关键字，可以快速找到对应代码。

4. **和编译器团队建立良好的沟通习惯**。你不需要自己 debug 所有问题，但你需要能"精准描述问题"——告诉编译器团队"在哪个 Pass 失败了，输入的 IR 大概长什么样，报了什么错"。

5. **你的独特价值**。编译器团队懂代码但不懂客户场景，你懂客户场景。你从闭源代码中学到的知识，加上你对客户模型和业务的理解，能让你成为客户和编译器团队之间最高效的桥梁。

## 十二、HLIEvLLM 编译器管线（对比参考）

HLIEvLLM 的 TorchCompile 管线与 Houmo 管线是两种不同的编译思路，可以对比学习：

```
PyTorch Model (nn.Module)
    │
    ▼  [Dynamo Tracing + torch.compile]
FX Graph
    │
    ▼  [PiecewiseCompileBackend]            ← 分段编译
Sub-graphs
    │
    ▼  [PostGradPassManager]                ← Fusion Passes
    │    - RMSNormQuantFusion
    │    - AttnQuantFusion
    │    - RopeKVCacheFusion
    │    - AllReduceRMSFusion
    │    - ...
    │
    ▼  [IR Lowering + Inductor Codegen]
Triton Kernels / Compiled Callable
```

| 维度 | Houmo/XH2 管线 | HLIEvLLM TorchCompile 管线 |
|------|---------------|--------------------------|
| 前端 | 自研 Merak (torch.fx) | PyTorch Dynamo |
| IR | HMONNX (ONNX 变体) | FX Graph |
| 优化 | 自研 hmatc ONNX Pass | torch.compile Inductor Pass |
| 后端 | TCIM Builder (MLIR + 芯片指令) | Inductor (Triton kernel 生成) |
| 目标 | XH2 NPU | NVIDIA/AMD GPU |

**对比学习建议**：读完 Merak 管线后，看一下 HLIEvLLM 的 `PostGradPassManager` 和 hmatc 的 ONNX Fusion Passes 在融合规则上的异同。

**相关文件**：
```
HLIEvLLM-1.4.0rc0/vllm/compilation/
  ├── passes/pass_manager.py        ← PostGradPassManager 主调度
  ├── passes/fusion/                ← 融合 Pass 集
  │   ├── rms_quant_fusion.py
  │   ├── act_quant_fusion.py
  │   ├── attn_quant_fusion.py
  │   ├── rope_kvcache_fusion.py
  │   └── allreduce_rms_fusion.py
  └── passes/ir/lowering_pass.py    ← IR 降级 Pass
```
